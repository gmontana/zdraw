# Engine architecture

This document is the authority for the engine's component boundaries and resource
lifetimes. Changes to those contracts must update both this document and the
corresponding tests or checks in `tools/style/architecture_guard.py`.

## 1. Release boundary

The public interface is the CLI: model download, generation, editing, interactive
sessions, diagnostics and benchmarking. This source tree includes its inference
engine, native Metal bridge, kernels and developer tools. It excludes native apps,
Swift packages and the native app's C interface. The release-boundary guard rejects
those components and missing static build inputs.

The CLI supports Z-Image-Turbo, FLUX.2 Klein 4B and its undistilled base checkpoint. Some internal
model variants and experimental execution controls remain because engine code
uses their types and hooks. Their presence is not a supported public API or a
performance claim. No external research repository is required to build or run.

## 2. Dependency direction

```text
CLI and interactive session
  -> model-neutral requests and profiles
  -> model runtimes and tensor operations
  -> Metal contexts, buffers, pools and kernels
  -> Objective-C Metal bridge
```

Lower layers execute validated requests. They do not choose model, quality tier,
precision policy or a route based on available RAM. `runtime_options.zig` owns
product profiles; `profile.zig` reports hardware capabilities. An explicit
`--profile` overrides environment settings; the default defers to exported
experiment flags. Every such flag is documented in [env-flags.md](env-flags.md).

## 4. Request and session invariants

`model_kind.zig` owns Klein's default-route dimension policy and the existing
4096-image-token capacity shared with `zflux2_run.zig`. With a 16-pixel token
stride, the half-activation GEMM's 32-row alignment requires an image area
multiple of 8192 pixels; width and height must each be divisible by 32 and
area must not exceed 1,048,576 pixels. CLI/session validation rejects other
shapes before loading or replacing model state. Synthetic preview bypasses
model constraints. This admission rule changes no numerical route or capacity.
Model-policy/parser tests, CLI smoke and the std-only policy import guard enforce
this contract. Exact tested shapes and visual limits are recorded separately.

The CLI owns resolved model paths until dispatch returns. A session borrows its
startup path and owns paths selected by model switching in `State.weights_owned`.
Failed swaps free temporary paths; successful swaps transfer them once.

A render transfers pixels to `saveCandidate`. Rejection or failure releases them;
a successful in-memory result transfers them to the session state. Automatic saves
encode the PNG, exclusively create an unused filename and return its owned path
only after writing succeeds. The state owns the last successful path. Repeated
and batched CLI generation has one cleanup owner for its current results.

Safety checks refuse before sampling or saving. The CLI maps refusal to exit
status 3; sessions keep the prompt open so terminal and resource cleanup run.
Invalid CLI inputs and recoverable runtime failures return errors. Assertions
protect internal invariants, never user-controlled shape or format validation.

Generation uses shared runtime state and must obey `genlock.zig`. Do not run
concurrent renders or bypass the lock. GPU tests also need an idle device.

## 5. Memory and lifetime invariants

### 5.1 Allocators

- A caller-provided allocator owns ordinary CPU allocations.
- A value that outlives the creating call either stores its allocator or is
  deinitialized with the same allocator.
- Partial initialization uses `errdefer` in reverse ownership order.
- Successful initialization transfers each owned value exactly once.
- `deinit` is called exactly once and leaves the value undefined; it is not
  idempotent.
- Product modules do not choose global allocators. The CLI receives the process
  allocator from its caller; engine modules borrow the allocator they are given.
- `page_allocator` is restricted to the named streamed-VAE phase allocators in
  `mvres_stream_chain.zig` and `vdecode.zig`; new sites fail the architecture
  gate.

Enforcement: Zig allocator parameters, `errdefer`/`defer`, the architecture
guard, the style ratchet, and leak-detecting unit-test allocators.

### 5.2 Owned and borrowed Metal buffers

`mbuffer.Buffer` carries explicit `owned` or `borrowed` state.

- `Buffer.empty`, `Buffer.fromBytes`, and `Buffer.fromInput` create owned
  buffers.
- `Buffer.borrow` creates a view of a handle owned by a pool or another
  aggregate.
- `Buffer.deinit` requires an owned buffer and fails loudly if called on a
  borrowed view; only the owner releases the Metal handle.
- Direct `mbuffer.Buffer{ .handle = ... }` construction outside `mbuffer.zig`
  is forbidden.
- An owned `Buffer` is linear: after ownership is transferred, the old value
  must not be used or deinitialized. Zig cannot enforce moves, so constructors,
  narrow scopes, and the architecture guard are the enforcement mechanism.
- Raw `zdraw_metal_release_buffer` calls are confined to the buffer/cache
  owners and explicit tool fixtures.

Enforcement: `Buffer.Ownership`, owning/borrowing constructors,
`Buffer.deinit`, architecture guard, and Metal tests.

### 5.3 Persistent pools

macOS may retain GPU wiring after an `MTLBuffer` is released. Resident paths
therefore use named, grow-only slots whose lifetime is the owning Metal
context:

- a slot grows to its high-water capacity and never shrinks during the context;
- every producer fully writes its live range before any read;
- contents are never assumed zero after reuse;
- a pooled handle is borrowed by an operation and must not be released there;
- the pool releases all owned buffers before its device is released;
- a slot whose dispatch path is mode-dependent may be materialized on first
  dispatch within its pool-shape lifetime (optional field, handle reachable
  only through the materializing accessor), so dead modes never allocate it.

Slot aliasing is legal only where the schedule proves lifetimes do not overlap.
Changing aliases or adding a slot requires a liveness review and strict-output
gate. The resident VAE mid-attention (`mvattn.zig`, `mvattn_owned.zig`)
borrows chain-pool slots (state/norm/q/k/v/mix/attn, and gate/ffn/up/gateup/
mod_in for the owned attention) while the denoise chain is idle, the same
non-overlap the biased-GEMM and pooled-attention paths already rely on.

Lending (`mlend.zig`) generalises that borrow across contexts. A lender is a
foreign pool that hands out one of its existing, idle buffers when its
capacity covers the request, and otherwise answers null; it never allocates
or grows, so a lender can only remove memory. The borrower fully rewrites a
lent buffer before reading it, exactly as it does its own slots, and falls
back to its own pool whenever the lender declines. The schedule that makes
every lend legal is the same one that makes the mid-attention borrow legal:
all GPU work is commit-and-wait, and the VAE decodes only after the denoise
has finished. The Klein resident DiT pool (`zflux2_resident.zig`) lends its
idle slots to the mid-attention during decode (a fixed slot map, checked
against the pool's size table; it declines while a batch is open, before the
first forward, and without the half scratch). Z-Image lends nothing to the
mid-attention, which keeps its direct chain-pool borrow.

Enforcement: `mchain_pool.Pool`, explicit slot enum, borrowed buffers, context
deinitialization order, strict image gates, and measured peak memory.

### 5.4 Mapped weights and no-copy buffers

Tensor views borrow bytes from mapped model files. No-copy Metal weight buffers
also borrow those bytes:

```text
mapped file > tensor view > no-copy Metal buffer/cache
```

The aggregate model runtime owns this ordering. It must destroy resident Metal
contexts and their buffer caches before unmapping transformer or sidecar files.
Views never close or unmap their source.

For packed sidecars, `mpacked.Cache` borrows `zpack_file.Mapped.bytes`; the
cache is destroyed before the sidecar mapping. A copied packed buffer instead
owns its Metal allocation and does not borrow the temporary CPU packing buffer.

Enforcement: aggregate runtime `deinit` order, no-copy cache ownership, mapped
types, and model-load tests.

### 5.5 CPU-to-GPU transfer

`Buffer.fromBytes` synchronously copies the supplied CPU bytes. The caller may
release them when it returns. `Buffer.fromInput` accepts an explicit `Recycle`
handoff and frees that CPU activation only after the synchronous copy has
completed; after passing `Recycle`, the caller no longer owns the slice.

Enforcement: the `Recycle` value and the single implementation in
`mbuffer.zig`.

### 5.6 Command-buffer lifetime

Buffers, pipelines, and mapped bytes referenced by encoded commands remain
alive until the owning command buffer has completed. A context may reuse
pooled storage only after the schedule's ordering guarantees the prior use has
ended. Replay and teardown paths drain outstanding work before releasing
resources.

Enforcement: resident batch boundaries, explicit waits/drains in replay,
context teardown, route-count checks, and the persistent replay memory gate.

### 5.7 Memory claims

Static liveness and resource bounds are admission aids, not measurements.
Product memory authority is the measured process physical footprint and GPU
live bytes from the real route. Cross-phase reuse is off unless implemented
and measured. A candidate exceeding a frozen memory budget fails even if its
latency improves.

One cross-phase reuse is implemented: the streamed VAE's `conv1_out` role
may be leased for one decode from an idle denoise buffer (`mvres_stream_chain`
`reserve`; Klein's `wide`, Z-Image's chain `gateup`; ledger
`memory-pass-20261004` in docs/experiments.jsonl). The lease is decided once at
presize and ends with `vdecode.run`, the lending pool pins or refuses to
reshape the lent buffer meanwhile, and a request above the lease fails rather
than growing a buffer the borrower does not own. Plan-level
`MemoryPolicy.cross_phase_reuse` remains rejected; the lease is a fixed
schedule fact, not a plan knob.

Enforcement: plan memory policy, execution receipt, memtrace/memgate, and
independent promotion.

### 5.8 Metal pipeline ownership

Every successful `mpipe.required` call transfers one owned pipeline object to
the calling context. Multi-pipeline contexts group those handles under one
aggregate owner, protect each successful construction immediately with
`errdefer`, and release every pipeline before releasing their device. Partial
initialization unwinds in reverse construction order. A raw pipeline handle is
borrowed by dispatch calls only.

Enforcement: context `init`/`deinit`, aggregate pipeline owners, the
architecture guard, and Metal context tests.

### 5.9 Progressive display

The CLI owns a stack `terminal_preview.View` around one synchronous Klein
render. It activates the embedded `progress_sink.Sink` only after the view is
at its final address, and deactivates it on every exit before freeing the view.
The thread-local observer rejects nesting. Callbacks borrow pixels for the
duration of the call and cannot retain them. Engine progress modules import
only the model-neutral sink, never terminal or CLI policy. Compact progress
bars also pass through this sink so their final newline cannot move the live
preview region.

The terminal view owns a bounded temporary image region, clears it before the
final image or an error is printed, and changes no terminal modes. It is enabled
only when image display is requested and both output streams are terminals of
sufficient size. Previews are approximate latent projections, not decoded final
images; they do not change sampling or the final safety check.

Enforcement: observer scope/error tests, terminal protocol tests, real-model
PTY checks, and the architecture guard's progress-module import boundaries.

## 6. Experimental controls and evidence

Plan/control modules have restricted imports enforced by the architecture guard.
Controls are scoped to an admitted plan, and teardown deactivates them. Unknown
fields, shapes, identities, unsupported routes and incomplete execution counts
are errors; an experiment cannot silently fall back and claim success.

An exact quality contract cannot contain lossy representations or work reduction.
Receipt fields bind the plan, source and realization hashes, model, workload,
output, thermal state and actual execution counts. A hash or timing by itself
does not establish a successful optimization.

Kernel changes require both model quality gates, a reproducibility census and
viewed images. Speed and memory claims follow the
[measurement protocol](measurement-protocol.md). Optional framework implementations
may remain as benchmark oracles; shipping inference uses the owned Metal routes.
